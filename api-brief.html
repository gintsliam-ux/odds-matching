worth a doc edit

The grouped buckets are already flat

group=fixture nests markets under the event, and I expected each entry to be a market holding a selections array. It isn't — h2h, spreads and totals are flat lists of selection rows carrying book_prices and book_fairs directly, which is the odds_sp shape the page already understood.

Good design; it just isn't written down. I shipped an unpacking loop for the nested shape and the event page rendered “0 price lines” until I looked at an actual market object. One line in the reference saves the next person that.

small, but it counts 1 fixture in 9,207

A fixture can land on both sides of a page boundary

Paging a soccer month returned 5,000 then 4,207 rows — 9,207 — but only 9,206 distinct fixture_ids. One row appears on both pages, so the range() boundary is not quite stable despite the fixture_id tiebreak after scheduled_start.

Harmless for the page, which dedupes anyway. It would not be harmless for anything that pages in order to count.

What this retired

A Node API on a laptop, a cloudflared tunnel whose hostname changed on every restart, and the vercel.json rewrite that chased it. Nine repoints, eight outages, each one invisible until somebody opened the page. vercel.json is deleted too — every request is same-origin or straight to the API, and a stale rewrite is exactly how a future merge would have broken it again.

Badges are the one thing with no endpoint behind it: 1,079 URLs snapshotted from entities. They change rarely enough that a file beats a service, and re-running the snapshot is one command if they drift.
